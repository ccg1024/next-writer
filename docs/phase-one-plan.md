# 阶段一执行计划：可靠性与效率基础

## 1. 阶段目标

阶段一的目标是让 Next Writer 具备可以承载真实写作工作的基础可靠性和效率能力：

- 用户能够明确知道文档当前是否已保存。
- 应用异常退出后，最近一次编辑内容可以恢复。
- 快速切换、自动保存和手动保存不会发生旧内容覆盖新内容。
- 外部程序修改文件时，应用不会静默覆盖用户内容。
- 用户可以通过全文搜索、最近打开、收藏和命令面板快速定位文档。
- 所有新增能力遵守现有主进程、渲染进程和 IPC 边界。

建议周期：4–6 周。

## 2. 阶段范围

### 2.1 本阶段包含

1. 文档会话与保存状态模型。
2. 自动保存、退出保存和缓存 flush。
3. 草稿恢复和异常退出恢复。
4. 外部文件变化检测和基础冲突处理。
5. 文件名和 Markdown 正文全文搜索。
6. 最近打开、收藏和置顶。
7. 命令面板初版。
8. 阶段性测试、性能基线和错误观测。

### 2.2 本阶段暂不包含

- 三方合并编辑器和复杂冲突合并算法。
- 云同步和多人协作。
- 全局知识图谱。
- 双向链接和标签索引。
- PDF、HTML 等发布能力。
- AI 改写和 AI 知识库问答。
- 可扩展插件市场。

## 3. 统一约束

所有模块必须遵守以下约束。模块可以独立实现，但不能绕过这些约束。

### 3.1 架构约束

- 主进程负责文件系统、工作区索引、持久化和窗口生命周期。
- 渲染进程负责编辑器状态、界面状态和用户交互。
- renderer 不直接访问 Node 文件系统或任意本地路径。
- 新增 IPC 必须同步修改 contract、请求校验、handler、preload 和 renderer gateway。
- 主进程服务依赖 `src/window/interface/` 中的接口，并通过容器注册。
- 所有跨模块数据使用明确的 TypeScript 类型，不使用隐式共享对象。

### 3.2 数据安全约束

- 未保存内容不能因为保存失败、切换文档或退出流程而被清除。
- 旧 revision 不得覆盖新 revision。
- 文件写入失败必须返回明确错误，不得静默吞掉异常。
- 删除、重命名和冲突处理不能破坏原始文件内容。
- 恢复草稿必须由用户确认后覆盖当前文档。
- 所有持久化格式必须支持版本号和未来迁移。

### 3.3 体验约束

- 保存状态必须在用户可见区域提供反馈。
- 自动保存不能阻塞输入，不能频繁弹窗。
- 异常和冲突提示必须告诉用户发生了什么，以及可以采取什么操作。
- 搜索结果应能定位到文件和具体匹配位置。
- 所有核心操作必须提供快捷键或命令面板入口。

### 3.4 测试约束

- 新增主进程逻辑必须有单元测试。
- 新增 renderer 状态逻辑必须有组件或状态测试。
- 保存、恢复、冲突和快速切换必须有回归用例。
- 每个模块完成前必须执行格式检查、lint 和相关测试。
- 不以“手动测试没有复现”作为数据安全问题的唯一验收依据。

## 4. 模块拆分总览

| 模块 | 主要职责 | 优先级 | 依赖 |
| --- | --- | --- | --- |
| A. 文档会话与状态模型 | 统一当前内容、磁盘快照、修改状态和 revision | P0 | 无 |
| B. 保存调度与缓存 flush | 自动保存、手动保存、退出保存和切换保存 | P0 | A |
| C. 草稿恢复 | 异常退出后保存和恢复临时内容 | P0 | A、B |
| D. 外部变更与冲突 | 检测磁盘变化并防止静默覆盖 | P0 | A、B |
| E. 工作区索引与全文搜索 | 文件名、正文和上下文搜索 | P0 | 工作区文件读取能力 |
| F. 最近打开、收藏与置顶 | 文档访问历史和用户快捷入口 | P0 | A、基础持久化 |
| G. 命令面板 | 统一暴露搜索、新建、打开、主题等命令 | P1 | E、F、现有 renderer command |

## 5. 模块计划

## 模块 A：文档会话与状态模型

### A.1 目标

将当前分散在编辑器组件、文档缓存服务和文档服务中的内容状态收敛为清晰的文档会话模型，为保存、恢复和冲突处理提供唯一状态来源。

### A.2 建议数据模型

```ts
type DocumentSessionStatus =
  | 'loading'
  | 'ready'
  | 'dirty'
  | 'saving'
  | 'saved'
  | 'save-error'
  | 'external-change'
  | 'conflict';

type DocumentSession = {
  id: string;
  path: string;
  content: string;
  savedContent: string;
  status: DocumentSessionStatus;
  localRevision: number;
  savedRevision: number;
  diskModifiedTime?: number;
  lastSavedAt?: number;
  lastError?: string;
};
```

实际类型应根据现有 `_types` 和 IPC contract 调整，避免同一状态在多处重复定义。

### A.3 任务拆分

1. 梳理现有 `DocumentService`、`DocumentCacheService`、`Main` 组件中的状态来源。
2. 定义文档会话状态、状态转换和错误结构。
3. 新增文档会话服务接口和实现。
4. 将当前文档内容、dirty 状态、revision 和保存时间迁移到会话服务。
5. 保留现有缓存 API 的兼容层，降低一次性改动风险。
6. 让编辑器只通过明确的 action 更新文档会话，不直接修改多个 ref。
7. 增加状态转换测试和快速切换测试。

### A.4 验收标准

- 任意时刻可以明确查询当前文档的内容、保存状态和 revision。
- 文档切换后，旧文档状态不会污染新文档。
- 编辑器组件不再单独维护保存状态的第二份事实来源。
- 非法状态转换会被拒绝或记录错误。

### A.5 交付物

- 文档会话类型和接口。
- 文档会话服务。
- 对应 IPC contract 和 renderer gateway 能力。
- 状态转换单元测试。
- 文档会话状态图或状态说明。

## 模块 B：保存调度与缓存 flush

### B.1 目标

建立统一保存调度机制，覆盖输入后的自动保存、用户主动保存、文档切换保存和应用退出保存。

### B.2 任务拆分

1. 抽取保存队列，统一处理保存请求和 revision。
2. 明确保存策略：
   - 输入后延迟自动保存。
   - 用户触发时立即保存。
   - 文档切换前 flush 当前文档。
   - 窗口关闭前等待保存结果。
3. 防止同一文档并发写入造成顺序错乱。
4. 保存成功后同步更新：
   - 文档会话状态。
   - 文件树中的修改时间和描述。
   - 窗口 dirty 状态。
   - 最近打开记录。
5. 保存失败后保留编辑器内容和 dirty 状态。
6. 增加自动保存配置，包括启用开关和延迟时间。
7. 将保存反馈接入标题栏、状态栏或编辑器外围区域。

### B.3 关键规则

- 自动保存不等于清除 dirty 状态；只有磁盘写入成功后才可以标记为已保存。
- 保存过程中继续输入时，不得用旧内容覆盖新内容。
- 保存失败后不能自动回退编辑器内容。
- 退出流程不能无限等待，应有超时和恢复草稿兜底。

### B.4 验收标准

- 输入后按照配置延迟保存。
- 快速输入、保存、继续输入时，最终磁盘内容等于最后一次有效内容。
- 保存失败时用户可以继续编辑并重试。
- 切换文档后返回原文档，最新内容仍然存在。
- 窗口关闭前，已进入保存队列的内容可以完成写入或进入恢复草稿。

### B.5 交付物

- 保存调度服务或保存队列。
- 自动保存配置项。
- 保存状态 UI。
- 退出和切换文档的 flush 流程。
- 保存顺序、失败和超时测试。

## 模块 C：草稿恢复

### C.1 目标

在异常退出、保存超时或应用崩溃后，为用户保留最近一次未写入磁盘的编辑内容，并提供可控恢复入口。

### C.2 任务拆分

1. 设计恢复草稿目录和文件命名规则。
2. 设计草稿元数据：文档 ID、原始路径、内容、revision、创建时间和来源。
3. 在以下时机写入草稿：
   - 自动保存失败。
   - 窗口关闭前保存未完成。
   - 定时恢复快照。
4. 应用启动时扫描可恢复草稿。
5. 当前文档打开时检测对应草稿。
6. 提供“恢复草稿”“查看差异”“忽略草稿”操作。
7. 成功保存恢复内容后清理草稿。
8. 为过期草稿设置清理策略，但不能误删近期草稿。

### C.3 安全要求

- 恢复草稿不能自动覆盖磁盘文件。
- 草稿写入采用临时文件加原子替换，避免生成损坏草稿。
- 草稿目录不应污染用户的 Markdown 工作区。
- 草稿内容和原始文件路径必须建立清晰关联。

### C.4 验收标准

- 模拟编辑后强制结束应用，重新启动可以发现恢复草稿。
- 用户忽略草稿后，原始文件内容不发生变化。
- 恢复后可以继续编辑并正常保存。
- 损坏或不完整草稿不会阻塞应用启动。

### C.5 交付物

- 草稿存储服务。
- 启动恢复检测流程。
- 草稿提示和恢复界面。
- 草稿格式版本和清理策略。
- 异常退出恢复测试。

## 模块 D：外部文件变更与冲突处理

### D.1 目标

识别外部编辑器、Git、同步工具或脚本对文件造成的变化，避免应用静默覆盖外部修改。

### D.2 任务拆分

1. 选择文件监听机制，并限制监听范围为当前工作区。
2. 记录打开文档的磁盘修改时间或内容指纹。
3. 文件变化时按状态分类：
   - 应用没有未保存内容：自动重新加载。
   - 应用有未保存内容，磁盘内容变化：进入冲突状态。
   - 文件被删除或移动：显示文件不可用状态。
4. 提供冲突处理初版：
   - 使用磁盘版本。
   - 保留本地版本。
   - 另存为新文件。
5. 冲突处理期间禁止自动保存覆盖磁盘版本。
6. 对文件重命名和工作区同步后的路径变化提供恢复策略。

### D.3 阶段边界

阶段一只要求可靠识别和保护数据，不要求实现完整三方合并。对比视图可以先提供文本差异摘要，复杂合并放入后续阶段。

### D.4 验收标准

- 外部修改未保存文档时，应用不静默覆盖外部内容。
- 未修改文档被外部修改时，可以自动刷新或由用户确认刷新。
- 文件被删除后，当前编辑内容仍可恢复或另存。
- 冲突状态下自动保存暂停。

### D.5 交付物

- 工作区文件监听服务。
- 文档磁盘快照或指纹机制。
- 外部变更 IPC 事件。
- 冲突提示界面和处理命令。
- 外部修改、删除和移动测试。

## 模块 E：工作区索引与全文搜索

### E.1 目标

提供工作区级别的文件名、标题和正文搜索，并为后续标签、双向链接和知识索引预留基础。

### E.2 推荐分阶段实现

#### E1：最小可用搜索

- 遍历工作区内 Markdown 文件。
- 支持文件名和正文关键词。
- 返回文件 ID、路径、匹配行、上下文和匹配位置。
- 支持大小写和简单模糊匹配。
- 搜索结果点击后打开对应文档并定位行。

#### E2：增量索引

- 建立文件内容索引。
- 文件新增、修改、删除时更新对应索引。
- 应用启动时检查索引版本并在必要时重建。
- 搜索期间不阻塞编辑器输入。

### E.3 任务拆分

1. 定义搜索请求、结果和错误类型。
2. 抽取工作区文件扫描能力，排除配置目录、草稿目录和非 Markdown 文件。
3. 实现最小搜索服务。
4. 设计索引持久化格式和版本号。
5. 实现增量更新入口，与文件监听模块衔接。
6. 实现搜索结果列表、上下文预览和定位。
7. 增加空结果、读取失败和大结果集处理。
8. 增加搜索快捷键和命令面板入口。

### E.4 性能要求

- 搜索不能在 renderer 中全量读取文件。
- 搜索结果应限制数量并支持继续加载。
- 单个超大文件不能拖慢整个工作区索引。
- 索引重建应可观察，并允许用户继续使用已打开文档。

### E.5 验收标准

- 可以搜索文件名、标题和正文。
- 搜索结果能显示上下文并定位到具体行。
- 修改文件后，搜索结果最终能够反映新内容。
- 删除文件后，不再返回失效结果。
- 1,000 个 Markdown 文件的工作区中，搜索不会明显阻塞界面。

### E.6 交付物

- 工作区索引服务。
- 搜索 IPC contract 和 renderer gateway。
- 搜索 UI 和定位能力。
- 索引格式说明和重建机制。
- 搜索性能测试样本。

## 模块 F：最近打开、收藏与置顶

### F.1 目标

让用户不依赖文件树即可快速回到高频使用的文档。

### F.2 数据范围

建议作为应用元数据存储，不写入 Markdown 文件内容：

- 最近打开的文档 ID、路径和时间。
- 收藏文档 ID。
- 置顶文档 ID。
- 最近打开数量上限。
- 无效路径清理时间。

### F.3 任务拆分

1. 定义元数据格式和版本号。
2. 设计最近打开记录的写入时机。
3. 文档成功打开后更新最近打开，不要在点击但读取失败时更新。
4. 增加收藏和取消收藏操作。
5. 增加置顶和取消置顶操作。
6. 文件删除、移动或重命名时同步修正记录。
7. 在首页、侧边栏或快速打开面板展示入口。
8. 提供清除最近记录能力。

### F.4 验收标准

- 最近打开列表顺序与实际成功打开时间一致。
- 重启应用后最近打开和收藏仍然存在。
- 文件删除或不可访问后，不会产生无法处理的死链接。
- 收藏和置顶不改变 Markdown 文件内容。
- 用户可以从最近打开或收藏直接进入文档。

### F.5 交付物

- 工作区元数据服务。
- 最近打开、收藏和置顶 IPC 能力。
- 对应 UI 和快捷命令。
- 元数据迁移和失效记录清理测试。

## 模块 G：命令面板

### G.1 目标

建立统一的命令发现入口，降低功能增加后菜单和快捷键分散的问题。

### G.2 第一版命令范围

- 搜索工作区。
- 快速打开文档。
- 新建笔记。
- 新建文件夹。
- 保存当前文档。
- 切换自动保存。
- 打开最近文档。
- 收藏或取消收藏当前文档。
- 切换主题。
- 切换打字机模式。
- 同步工作区。

### G.3 任务拆分

1. 定义命令类型：ID、标题、分类、快捷键、执行函数和可用条件。
2. 建立 renderer 命令注册表。
3. 支持模糊匹配和分类展示。
4. 支持当前上下文过滤，例如没有打开文档时禁用保存。
5. 支持键盘导航、Enter 执行和 Escape 关闭。
6. 将已有 renderer command 和菜单行为逐步接入统一命令。
7. 记录命令执行错误并显示用户可理解的反馈。

### G.4 验收标准

- 用户可以通过一个快捷键打开命令面板。
- 可以搜索并执行阶段一核心命令。
- 不可用命令会被禁用或明确提示原因。
- 命令执行结果与菜单、快捷键触发结果一致。
- 新增命令不需要复制大量 UI 逻辑。

### G.5 交付物

- 命令类型与注册表。
- 命令面板组件。
- 阶段一命令集合。
- 键盘交互测试。

## 模块 H：阶段质量与观测

### H.1 目标

让阶段一的可靠性目标可验证、可回归、可定位，而不是只依赖用户反馈发现问题。

### H.2 测试任务

#### 主进程

- 文档会话状态转换。
- 保存 revision 顺序。
- 自动保存失败。
- 退出保存和 flush 超时。
- 草稿写入、扫描和清理。
- 外部修改、删除和冲突。
- 搜索索引新增、修改和删除。
- 最近打开和收藏元数据迁移。

#### 渲染进程

- 保存状态展示。
- 文档切换时状态恢复。
- 搜索结果点击定位。
- 恢复草稿提示。
- 冲突提示和操作。
- 命令面板键盘操作。

#### 手工回归

- 连续切换多个未保存文档。
- 输入后立即关闭应用。
- 模拟保存失败后重试。
- 使用外部编辑器修改当前文件。
- 删除当前文件后继续编辑并另存。
- 在大量文件工作区中搜索。

### H.3 观测信息

不记录用户文档正文，只记录必要的运行信息：

- 保存开始、成功、失败和耗时。
- 恢复草稿创建和恢复结果。
- 外部变更和冲突次数。
- 搜索耗时、结果数量和索引耗时。
- 文档切换耗时。
- 未捕获异常和 handler 错误。

### H.4 验收标准

- 关键链路都有自动化回归用例。
- 出现保存或恢复失败时，可以从日志定位原因。
- 可以获得阶段性能基线，而不是只描述“快”或“慢”。
- 所有新增测试、lint 和格式检查通过。

## 6. 模块依赖与并行安排

```text
模块 A 文档会话
        │
        ├── 模块 B 保存调度 ── 模块 C 草稿恢复
        │                  └── 模块 D 外部变更与冲突
        │
        ├── 模块 F 最近打开/收藏
        │
        └── 模块 G 命令面板

模块 E 工作区索引/全文搜索 ── 模块 G 命令面板

模块 H 质量与观测贯穿全部模块
```

推荐并行方式：

- 主线一：A → B → C / D，负责数据可靠性。
- 主线二：E，负责搜索和索引，可以与 B 并行。
- 主线三：F，依赖少，可与 A、E 并行，但需统一元数据存储。
- 汇总线：G，在 E、F 的最小能力完成后接入。
- 质量线：H 从第一天开始，不在阶段末尾集中补测试。

## 7. 建议迭代节奏

### 第 1 周：设计与基础模型

- 完成 A 的状态模型和接口设计。
- 明确保存、恢复、冲突、索引和元数据的数据格式。
- 补充 IPC contract 设计。
- 建立阶段测试样本：普通文档、长文档、1,000 文件工作区和损坏文件。

### 第 2 周：完成文档会话和基础保存链路

- 完成 A 的最小实现。
- 完成 B 的保存队列、revision 和手动保存。
- 接入基础保存状态 UI。
- 建立快速切换和异步保存回归测试。

### 第 3 周：自动保存、退出 flush 和草稿恢复

- 完成 B 的自动保存和退出流程。
- 完成 C 的草稿写入、扫描和恢复入口。
- 验证异常退出、保存失败和窗口关闭场景。

### 第 4 周：外部变更和全文搜索

- 完成 D 的文件监听、状态判断和冲突保护。
- 完成 E1 的最小可用搜索。
- 接入搜索 UI、结果上下文和行定位。

### 第 5 周：索引、最近打开和收藏

- 完成 E2 的增量索引基础。
- 完成 F 的最近打开、收藏和置顶。
- 处理文件删除、重命名和移动后的元数据清理。

### 第 6 周：命令面板与阶段验收

- 完成 G 的命令注册、搜索和键盘交互。
- 汇总 A–G 的端到端回归测试。
- 执行大工作区和长文档性能测试。
- 关闭阻塞性问题，形成阶段复盘和下一阶段输入。

## 8. 阶段总验收标准

阶段一完成必须同时满足以下条件：

### 可靠性

- 正常保存、自动保存、切换文档和退出应用均有明确行为。
- 保存失败不会丢失编辑器中的内容。
- 异常退出后可以恢复最近一次未保存内容。
- 外部修改不会被静默覆盖。
- 旧 revision 不会覆盖新 revision。

### 效率

- 可以搜索文件名和正文，并定位到具体行。
- 可以从最近打开、收藏或置顶入口快速回到文档。
- 可以通过命令面板执行阶段一核心操作。
- 搜索和索引不明显阻塞输入和编辑。

### 工程质量

- 新增能力均通过统一 IPC 边界。
- 关键主进程和渲染进程逻辑具有自动化测试。
- 关键错误有可追踪日志。
- 建立了长文档和大工作区性能基线。
- 格式检查、lint 和相关测试通过。

## 9. 阶段结束后的决策门

阶段一结束时，根据以下结果决定是否进入阶段二：

- 如果保存、恢复或冲突链路仍存在数据风险，阶段二暂停，优先修复可靠性问题。
- 如果搜索在大工作区中性能不达标，先优化索引，不继续叠加知识连接功能。
- 如果编辑器长文档输入和滚动不稳定，先减少或重构高成本 decoration 插件。
- 如果用户对命令面板和最近打开的使用频率低，优先通过可用性反馈调整入口，不急于扩展命令数量。
- 只有数据可靠性、搜索效率和编辑器性能达到基线后，才进入语义化混合编辑阶段。

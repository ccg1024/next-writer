# Next Writer 整体项目规划

## 1. 文档目的

本文档用于规划 Next Writer 下一阶段的产品演进、技术建设和版本节奏，作为后续需求拆解、Issue 排期和阶段验收的统一依据。

本文档基于当前项目能力制定。当前项目已经具备本地 Markdown 知识库、文件树、CodeMirror 混合编辑、文档大纲、主题系统、图片内联预览和打字机模式等基础能力。

## 2. 产品定位

Next Writer 的目标不是成为另一个传统 Markdown 编辑器、知识库或在线协作文档，而是形成以下产品组合：

> 本地文件的开放性 + 低干扰的混合编辑 + IDE 式效率工具 + 轻量知识连接。

核心用户价值：

- 用户可以直接管理和使用本地 Markdown 文件，不被专有数据格式锁定。
- 用户可以在保留 Markdown 可读性的同时，减少语法符号对写作的干扰。
- 用户可以快速搜索、组织和定位文档，而不是只依赖文件夹浏览。
- 用户可以逐步建立笔记之间的链接和上下文关系。
- 用户始终知道内容是否保存、是否安全、是否可以恢复。

## 3. 当前基线与主要问题

### 3.1 已有基础

- Electron + React + TypeScript 的桌面应用架构。
- 主进程与渲染进程边界清晰，已有 IPC contract、preload 和 renderer gateway。
- CodeMirror 编辑器已支持 Markdown 语法解析、历史记录、搜索、折叠、列表、引用、代码块和图片等扩展。
- 已有本地工作区、目录树、笔记创建、重命名、删除和同步能力。
- 已有文档缓存和 revision 机制，可以避免部分异步保存覆盖问题。
- 已有大纲、主题、深色模式和打字机模式等差异化基础。

### 3.2 当前主要短板

- 保存、恢复、外部文件变化和冲突处理尚未形成完整的文档状态模型。
- 文档缓存主要存在于内存中，崩溃恢复能力有限。
- 目前缺少知识库级全文搜索、最近打开、收藏和快速命令入口。
- 文件树更偏向目录映射，产品元数据与文件系统状态尚未充分分离。
- 混合编辑能力主要集中在视觉装饰，标题、列表、引用、链接等语义操作还不够完整。
- 尚未建立双向链接、反向链接、标签和文档关系等知识连接能力。
- 主题系统已有 token 基础，但缺少完整设置界面、主题预览和编辑体验配置。
- 缺少针对大文档、插件生命周期、文件冲突和异常退出的系统性测试。

## 4. 总体目标

### 4.1 产品目标

在后续几个版本内，将 Next Writer 从“有特色的 Markdown 编辑器”提升为“可靠、快速、可连接的本地写作工具”。

### 4.2 技术目标

- 建立统一的文档会话与保存状态模型。
- 保持主进程、渲染进程和 IPC contract 的清晰边界。
- 让编辑器插件具备可组合、可增量更新、可测试和可销毁的生命周期。
- 为全文索引、文档元数据、历史版本和双向链接预留稳定的数据层。
- 以大文档性能、异常恢复和数据安全为重要质量指标。

### 4.3 非目标

当前阶段暂不以以下内容为优先目标：

- 复杂的多人实时协作。
- 重型云端同步平台。
- 大规模插件市场。
- 依赖 AI 才能使用的核心编辑流程。
- 以全局关系图谱为中心的产品体验。

## 5. 优先级原则

采用以下优先级判断：

| 优先级 | 含义         | 判断标准                                 |
| ------ | ------------ | ---------------------------------------- |
| P0     | 必须优先完成 | 影响数据安全、稳定性、基本效率或用户信任 |
| P1     | 核心差异化   | 能显著提升编辑体验，并形成产品特色       |
| P2     | 增长与扩展   | 完善生态、发布能力和高级场景             |
| 暂缓   | 当前不投入   | 复杂度高、验证成本高或不影响近期核心价值 |

## 6. 版本路线图

### 阶段一：可靠性与效率基础

建议周期：4–6 周。优先级：P0。

阶段目标：让用户可以放心地使用 Next Writer 编写真实文档，不担心内容丢失，也不需要依赖目录逐层查找文件。

#### 主要任务

1. 建立文档状态模型
   - 定义文档会话状态：加载中、已加载、编辑中、保存中、已保存、保存失败、外部冲突。
   - 统一当前内容、磁盘内容、缓存内容和保存 revision。
   - 将当前散落在组件 ref、缓存服务和文档服务中的状态逐步收敛到文档会话服务。

2. 完善保存和恢复
   - 增加保存中、已保存、未保存、保存失败等明确状态反馈。
   - 支持可配置的自动保存。
   - 应用退出、窗口关闭和切换文档时统一 flush 缓存。
   - 增加异常退出后的草稿恢复。
   - 保存失败时保留本地内容，并提供重试入口。

3. 外部文件变化与冲突处理
   - 监听当前工作区内文件的外部修改。
   - 未修改状态下，自动重新加载外部内容。
   - 本地和磁盘内容均有修改时，提示用户选择保留本地、使用磁盘或进入对比合并。

4. 全文搜索与快速定位
   - 支持文件名和 Markdown 正文搜索。
   - 展示匹配上下文和具体行号。
   - 支持按路径、标题、标签、修改时间筛选。
   - 对常用笔记建立增量索引，避免每次搜索都全量遍历文件。

5. 基础效率能力
   - 最近打开的笔记。
   - 收藏和置顶。
   - 快速打开入口。
   - 命令面板初版。
   - 常用操作快捷键和快捷键帮助。

#### 阶段验收标准

- 模拟应用异常退出后，最近一次编辑内容可以恢复。
- 连续快速切换文档和保存，不出现旧内容覆盖新内容。
- 外部编辑器修改当前文件时，应用能够正确提示或刷新。
- 在包含至少 1,000 个 Markdown 文件的工作区中，搜索结果可以在可接受时间内返回。
- 用户可以通过一个快捷入口完成搜索、新建、打开最近文件和切换主题。

### 阶段二：语义化混合编辑

建议周期：6–8 周。优先级：P1。

阶段目标：让用户感受到自己在编辑文档结构，而不是手动维护 Markdown 语法。

#### 主要任务

1. 标题与大纲操作
   - 大纲显示当前章节高亮。
   - 支持从大纲拖拽调整章节顺序。
   - 支持章节折叠和章节级专注模式。
   - 显示章节字数和阅读时间。
   - 支持复制目录和生成目录。

2. 语义块操作
   - 列表支持 Tab、Shift+Tab、上下移动和连续缩进。
   - 引用块支持快速创建、拆分和转换。
   - 代码块支持语言选择、复制代码和快速切换。
   - 表格提供基础的行列增删和对齐操作。
   - 链接支持快速编辑、打开和预览。

3. 图片和附件体验
   - 支持拖入图片和粘贴图片。
   - 自动将图片保存到工作区附件目录。
   - 支持复制图片路径、替换图片和打开原图。
   - 图片加载失败时显示明确状态和修复入口。

4. 编辑器视觉和交互稳定性
   - 光标附近显示必要语法标记，离开后恢复低干扰状态。
   - 统一不同语法插件的选区、光标和 decoration 行为。
   - 解决大文档滚动、图片测量、折叠和语法隐藏之间的交互问题。

#### 阶段验收标准

- 标题、列表、引用、代码块、表格和图片均有至少一个可发现的语义操作入口。
- 大纲调整章节后，原文内容、链接和保存状态保持正确。
- 在长文档中滚动和输入时无明显光标跳动、内容闪烁或持续卡顿。
- 图片拖入、粘贴、保存、重新打开和删除流程完整可用。

### 阶段三：知识连接

建议周期：6–10 周。优先级：P1。

阶段目标：让笔记从孤立文件变成可以相互引用、追踪和探索的知识网络。

#### 主要任务

1. 双向链接
   - 支持 `[[笔记名称]]` 语法。
   - 输入时提供笔记补全。
   - 点击链接跳转到目标笔记。
   - 目标不存在时支持快速创建。

2. 反向链接
   - 当前笔记显示被哪些文件引用。
   - 展示引用上下文和所在行。
   - 支持从反向链接直接跳转。

3. 标签与虚拟分类
   - 支持文档内标签。
   - 标签自动索引和筛选。
   - 支持收藏、标签、最近修改等虚拟视图。
   - 文件夹仍保留为真实目录，不强制用户改变现有文件组织方式。

4. 文档索引与关系数据
   - 建立标题、链接、标签、修改时间等轻量索引。
   - 文件系统变化后增量更新索引。
   - 优先提供当前文档的局部关系视图，不急于建设复杂全局图谱。

#### 阶段验收标准

- 用户可以通过补全创建和跳转双向链接。
- 当前笔记的反向链接结果与工作区内容保持一致。
- 标签可以被搜索和筛选，且不破坏原始 Markdown 文件。
- 外部修改、文件重命名和文件移动后，索引能够恢复或重新建立。

### 阶段四：发布、生态与智能能力

建议周期：前述阶段稳定后再排期。优先级：P2。

#### 主要任务

- HTML、PDF、纯文本和带附件的文档导出。
- 工作区导入、导出与迁移工具。
- Git 状态查看和版本提交辅助。
- 主题编辑器、主题导入导出和主题预览。
- 可控的编辑器插件 API。
- AI 辅助改写、摘要、标题生成、标签建议和链接建议。
- 多工作区支持。
- 可选的同步能力。

AI 能力必须采用“选中内容 → 生成结果 → 预览 → 接受或撤销”的流程，不应直接覆盖用户原文，也不应成为核心编辑流程的前置依赖。

## 7. 技术拆分计划

### 7.1 文档会话与保存层

建议新增或逐步形成以下职责：

```text
DocumentSessionService
├── 当前文档内容
├── 磁盘快照
├── 本地修改状态
├── 保存队列与 revision
├── 自动保存
├── 草稿恢复
└── 外部文件冲突
```

实现原则：

- 文档内容的唯一状态来源应清晰可追踪。
- 保存操作必须幂等，且不能被旧 revision 覆盖。
- 保存失败不能清除未保存内容。
- 关闭窗口前必须有统一的保存和恢复策略。

### 7.2 工作区元数据层

文件系统继续作为 Markdown 内容的事实来源，同时将以下信息从目录树中分离出来：

- 最近打开记录。
- 收藏和置顶。
- 标签索引。
- 文档历史。
- 搜索索引。
- 双向链接索引。
- 用户自定义排序。

这样既能保持文件开放性，也能避免将产品状态全部绑定到文件树 JSON。

### 7.3 IPC 与安全边界

所有新能力必须遵守以下顺序：

1. 在 `src/window/ipc/ipc-contract.ts` 定义请求、响应和错误结构。
2. 增加主进程 handler，并通过接口注入服务。
3. 更新 preload 暴露能力。
4. 更新 renderer gateway 和调用方。
5. 增加请求校验、发送方校验和单元测试。

渲染进程不直接访问文件系统，不直接持有不必要的主进程对象，也不绕过 IPC contract。

### 7.4 编辑器插件规范

每个编辑器插件应明确：

- 负责的语法或交互范围。
- decoration 的创建和更新策略。
- 文档变更时如何增量计算。
- 选区和光标进入时如何恢复语法。
- 插件销毁时如何清理事件、缓存和 DOM。
- 大文档下的性能边界。
- 至少一个语法测试和一个交互测试。

## 8. 质量与测试计划

### 8.1 单元测试

- 文档状态转换。
- 保存 revision 和异步保存顺序。
- 外部修改检测和冲突判断。
- 文件路径安全和工作区边界。
- 搜索索引增量更新。
- 标签、链接和反向链接解析。
- 主题 token 校验。

### 8.2 渲染器测试

- 文档切换时编辑器内容正确加载。
- 修改、保存、失败和恢复状态正确展示。
- 大纲与编辑器位置同步。
- 图片、链接、列表、引用和代码块交互。
- 命令面板和快捷键。

### 8.3 手工回归场景

- 连续切换多个未保存文档。
- 快速输入后立即退出应用。
- 外部编辑器修改当前文档。
- 删除、重命名和移动文件夹。
- 大量图片和长文档滚动。
- 工作区中存在无效 Markdown、损坏配置和缺失图片。
- 系统浅色 / 深色模式切换。

### 8.4 性能基线

建议建立以下基线并持续监测：

- 应用启动到可输入时间。
- 搜索首个结果响应时间。
- 1,000 个文件工作区加载时间。
- 10 万字文档打开和滚动表现。
- 图片加载失败对编辑器的影响。
- 自动保存期间的输入延迟。

## 9. 产品指标

建议每个阶段至少关注以下指标：

- 保存失败率。
- 异常退出后的内容恢复成功率。
- 文档切换时内容丢失次数。
- 全文搜索响应时间。
- 大文档输入延迟和滚动稳定性。
- 用户从打开应用到开始输入的时间。
- 最近打开和搜索功能的使用频率。
- 双向链接创建和跳转次数。
- 用户连续使用天数和每次打开的编辑时长。

## 10. 风险与应对

| 风险                               | 影响                         | 应对策略                             |
| ---------------------------------- | ---------------------------- | ------------------------------------ |
| 保存状态继续分散在多个组件和服务中 | 数据覆盖、恢复困难           | 优先建设文档会话服务和状态机         |
| 编辑器插件越来越多导致性能下降     | 长文档不可用                 | 统一插件规范，优先增量更新和性能测试 |
| 文件系统与应用索引不一致           | 搜索、链接和打开失败         | 文件系统作为事实来源，索引支持重建   |
| 过早引入云同步                     | 架构复杂度和冲突成本大幅上升 | 本地可靠性完成后再验证同步需求       |
| AI 功能过早侵入编辑流程            | 用户失去控制，产品定位模糊   | 采用可预览、可撤销的局部操作         |
| 只追求视觉效果而忽视基础效率       | 使用频率低、留存差           | P0 功能完成前限制装饰性功能投入      |

## 11. 首批可执行任务

建议将以下任务作为下一轮迭代的直接入口：

1. 设计并实现文档状态类型和状态转换测试。
2. 将保存状态从 `Main` 组件中的多个 ref 收敛到独立服务。
3. 增加应用退出前的缓存 flush 和恢复草稿机制。
4. 增加当前文档的外部修改检测。
5. 设计全文搜索 IPC contract 和最小可用搜索界面。
6. 增加最近打开记录和收藏状态。
7. 设计命令面板的命令注册结构。
8. 为长文档建立编辑器性能测试样本。
9. 为标题大纲增加当前章节高亮。
10. 设计双向链接的 Markdown 语法、索引和跳转协议。

## 12. 最终优先顺序

如果资源有限，按以下顺序推进：

1. 保存可靠性、恢复和冲突处理。
2. 全文搜索、最近打开、收藏和命令面板。
3. 语义化标题、大纲、列表、链接和图片操作。
4. 双向链接、反向链接和标签索引。
5. 主题编辑器、发布能力和工作区扩展。
6. AI、Git、同步和插件生态。

Next Writer 的核心竞争力应建立在“内容可靠、写作顺畅、结构清晰、文件开放”之上。只有先完成这条主链路，后续的知识图谱、AI 和生态能力才有稳定的产品基础。
